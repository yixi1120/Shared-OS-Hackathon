## 2. 必须先解决的官方信息冲突

### 时间冲突

| 来源 | 原页面时间 | 北京时间（EDT 加 12 小时） |
|---|---|---|
| 主办方赛事页 | 开发期 2026-09-09 至 09-11；Arena 为 09-11 21:00–23:00 ET | Arena 为 09-12 09:00–11:00 |
| MentorMates | 09-11，提交关闭 21:00；正文误写 Wednesday，页首写 Friday | 如采用该日期，提交关闭为 09-12 09:00 |
| Devpost 精确赛程 | 提交 09-11 00:00 EDT 至 09-13 09:00 EDT | 09-11 12:00 至 09-13 21:00 |
| Devpost 精确赛程 | 评审 09-13 09:00–11:00 EDT；11:00 公布结果 | 09-13 21:00–23:00；23:00 公布结果 |

这些时间不能同时成立。不能擅自将 Devpost 的评审时间等同 Arena 时间，也不能认定较晚截止时间有效。建议按较早 Arena 时间倒排准备，同时由队伍在 Discord #arena-support 获取最终公告；此处尚未代发消息。

### 其他不一致

1. MentorMates 与 Devpost 规则均称六条有效性条件，但实际只展示五条。缺失内容未知，不能编造第六条。
2. 赛事页要求产品智能体在 SharedOS Cloud kernel 上运行；通用产品介绍却说明内核运行在应用内，Cloud 是决策可视化预览。必须采用主办方为本次活动提供的文档和接入环境，不能用普通本地库集成冒充赛事 Cloud 审计合格。
3. 宣传强调无人类评委，但 Judges’ Pick 明确由主办方评审。准确表述：Agents’ Choice 和 Top Earner 由智能体排名及交易决定，Judges’ Pick 有人工评审。
4. Devpost 摘要显示 $5,500 in cash，但奖项细目合计是 $500 现金及 $5,000 SharedOS API 额度。
5. Top Earner 只计算 counted credits，但当前完整规则页没有其计算细则；退款、自购、关联交易、失败交付等如何计分尚需主办方澄清。

## 4. 产品技术要求：逐项验收

依据 Devpost What to Build 与主办方赛事说明。

| 编号 | 必须满足 | 完成标准及建议保存的证据 |
|---|---|---|
| P01 | 产品智能体的 turns 在比赛要求的 SharedOS Cloud kernel 运行 | 真实运行记录可由 purpose string 和 agent addresses 检索；仅安装包或模拟日志不算 |
| P02 | grants 指定每个智能体可访问的文件和工具，默认拒绝 | 权限表；允许调用和越权拒绝的真实审计记录 |
| P03 | 工作流使用一致的 purpose string | 代码配置、运行记录与提交材料一致 |
| P04 | 至少一个 SharedNet 可发现、可调用的服务 | 另一节点成功发现并完成真实请求 |
| P05 | 明确服务说明、输入、输出、Arena credits 价格 | 服务清单与实际接口一致；每个服务一段说明 |
| P06 | 每次调用五分钟内交付 | 请求与交付时间戳；正常、失败和超时路径演练，不能把失败响应当作成功交付 |
| P07 | SharedOS 集成和 Arena 服务在开发期内构建 | 开发提交、构建与部署记录；官方开发期冲突需先确认 |
| P08 | 支持整场可达与无人干预 | 两小时演练、进程恢复及重复请求处理；这些是验收建议而非官网另加规则 |

服务领域不限，也可服务人类，但必须有面向智能体的真实调用能力。主办方列举研究、核验、代码审查、数据检索、翻译、跨智能体日程协调、长期记忆、谈判和监控。

## 5. Arena 硬性行为要求

依据 [Devpost Rules](https://shared-os-hackathon.devpost.com/rules)。任何一项缺失均可能使参赛无效。

| 编号 | 要求 | 验收证据 |
|---|---|---|
| A01 | 整场在线、产品整场可达 | 全场健康与服务日志；最终时间待确认 |
| A02 | Round 1 试用至少三个其他产品 | 至少三个不同产品的真实调用及结果 |
| A03 | 对每个试用过的产品至少发表一个具体异议 | 逐产品对应的公开评价记录；基于真实结果，不能只写泛泛评价 |
| A04 | Round 1 提交排名 | 排名提交成功回执 |
| A05 | Round 2 初始 100 credits 中花费至少 80 | 真实成交记录与预算汇总；未成交订单不当作花费 |
| A06 | Round 2 购买至少三个不同产品 | 至少三个产品标识及对应交易记录 |
| A07 | Arena 中无人类手动参与消息、排名、买卖、交付或修复 | 赛前准备完成；赛中智能体自主执行与日志 |

实现建议：将产品试用、异议、排名、交易与余额作为独立持久状态；交易前校验预算；失败后自动选择替代产品；重启后恢复进度并避免重复支付。建议是工程设计方向，尚不是已完成的代码。

## 6. 正式提交清单

依据 Devpost What to Submit。

- [ ] Devpost 项目页：项目名、tagline、产品用途、出售的服务。
- [ ] 代表智能体的真实 SharedNet node ID。
- [ ] 每个服务一段说明：名称、作用、输入输出、Arena credits 价格、SharedNet 调用方式。
- [ ] 真实 purpose string 与产品智能体地址，能够定位审计轨迹。
- [ ] 代码仓库链接：公开，或已给评委私有仓库读取权限。
- [ ] 队长 Discord 用户名。
- [ ] 可选：不超过两分钟的智能体跨服务真实调用视频。

不得用待填占位符、模拟节点、虚构交易或示例审计记录作为正式提交证据。
